# LocZ — 23 August 2026

A day's work on a live directory, written so it can be picked up on another machine. It covers
what changed, what broke, and the two faults that came closest to costing something real.

The directory went from **3,414,974 businesses to 4,207,872**, and from artwork on 37% of
pages to 98.7%. Along the way the production database went into crash recovery once, and it
was discovered that it had never been backed up.

---

## 1. The two things that mattered most

### The database had no backups

Not "stale backups" — none. The server held dumps for two unrelated applications from May and
August, and the CyberPanel cron jobs on the box back up web files, not Docker named volumes.
4.2 million businesses and a full day of enrichment had nothing to restore from.

Fixed: `/usr/local/bin/locz-backup.sh`, nightly at 02:30, keeping seven days. It writes to a
`.partial` name and moves on success, and **verifies each dump with `pg_restore -l` before
pruning the old ones** — a backup that cannot be listed cannot be restored, and finding that
out during an outage is the wrong time.

### An ad-hoc query took the site down

This looks harmless and is not:

```sql
SELECT ... FROM businesses JOIN categories JOIN cities ... ORDER BY random() LIMIT 5
```

It returns five rows, and to pick them it generates a random value for all 4.2 million and
builds hash tables over the whole table. The backend reached 3.5 GB, the host OOM killer took
it, and PostgreSQL went into crash recovery. The site was down about a minute; nothing was
lost (redo was 1.4 MB, recovery a tenth of a second).

The container had **no memory limit**, so a single query could take the entire 15 GB machine —
which also runs another application's database.

Fixed two ways:

- `docker update --memory 8g --memory-swap 8g locz-postgres`
- `scripts/business-enrichment/_db.py`: every connection now carries a statement timeout, a
  `work_mem` ceiling and no parallel workers, and `chunks()` walks large tables by key rather
  than by OFFSET. Offset re-reads every skipped row: paging 4.2M in 5,000s costs about 1.7
  billion row reads.

## 2. Data

### Import completed

793,045 businesses. The run had died at 628,000 on `PostgreSQL text fields cannot contain NUL
(0x00) bytes` — a few Overture names carry control characters, and one bad byte rejects a
whole 2,000-row batch. Scrubbed at the point the row is built rather than at insert, because
the slug, keywords and address all derive from those strings.

Coverage across all 4,207,872:

| field    | count     | %    |
| -------- | --------- | ---- |
| keywords | 4,207,872 | 100% |
| address  | 3,793,581 | 90%  |
| phone    | 2,962,577 | 70%  |

### Mandal: a correction

Reported as 0% populated, written into the Nominatim runbook as the sole reason to install it,
and repeated in a report sent onward. **It was wrong.** 147,500 localities carried a mandal,
reaching about 900,000 businesses.

Checking the values rather than the count found it. A random sample returned real mandals
(Surgana, Chikhli, Narsipatnam) beside plain district names (Varanasi, Katihar). Two classes
were provably useless and were cleared:

- 578 localities held the literal string **"Nil"**, which would have printed as though it were
  a place
- 30,023 held a "mandal" identical to their own city

116,899 remain. The correction strengthens the case for Nominatim rather than weakening it: it
is the only source that reliably distinguishes a mandal from the district containing it, so it
has values to _correct_ as well as gaps to fill.

### Duplicates: measured, deliberately not merged

`scripts/business-enrichment/duplicate_audit.py`, over 4,197,938 businesses:

```
probable duplicate pairs   8,111   (0.19% of records)
  0.90+ near certain       1,333
  0.75-0.89 likely           224
  0.50-0.74 uncertain      6,554
```

Nine near-certain pairs were checked against the structured data on their live pages: **nine
of nine are genuine duplicates**. Two that failed an exact string comparison turned out to be
the same place transcribed differently — "No. 353/1833/2087, Chandrasekharpur" against "Plot
No 353/1833/2087, Chandrasekhrpur" — both sharing a phone number. The exact-match check was a
cruder test than the score it was auditing.

**Nothing was merged, and the recommendation is not to.** 0.03% duplication has no measurable
effect on crawling or ranking, while every merge 301s a real page away permanently. _Central
Polytechnic College_ appears as five records across 65 metres: plausibly one campus,
plausibly separate departments a student would want to find individually. A script cannot tell,
and neither could I.

The real fix is upstream. The importer is idempotent on `sourceRecordId`, which catches a
re-run of the same source but not the same shop appearing twice in Overture under two ids.

## 3. Pages

### Category artwork: 37% → 98.7%

|             | categories | businesses |
| ----------- | ---------- | ---------- |
| own artwork | 621        | **98.7%**  |
| borrowed    | 499        | 1.1%       |
| none        | 286        | 0.2%       |

771 desktop and 771 mobile banners, 76 MB. Generated externally against
`docs/BANNER_GENERATION_BRIEF.md` and a round-2 brief.

The matcher needed three fixes, each found by looking at what it actually produced:

1. **Verbs are not identities.** "IT Services & Repair" took the _bike repair_ banner on the
   strength of sharing the word "repair". Repair, supply, dealer and agency describe what a
   trade does, not what it looks like.
2. **It is which word, not how many.** Requiring two shared words fixed that and broke a
   correct match: "Theme restaurants" and "Indian restaurants" share only "restaurants", which
   is exactly the word that should decide it. The rule is the **head noun** — the last
   significant word — because that is the thing the business _is_, while a modifier is a
   coincidence.
3. **Some head nouns are too generic.** "Dental clinics & tooth **care** centres" matched
   _hair **care**_, so a dentist was illustrated with combs and hair oil. Police and train
   **stations** matched _EV charging stations_. Those words may still count toward a two-word
   match; they cannot carry one alone.

`scripts/ui-verify/audit-banners.mjs` resolves every in-use category through the live matcher
and reports what it lands on. Checking by opening pages is how the dentist was missed.

### The storefront hero

The banner is now the background of the hero rather than a strip above a separate card. On a
phone that inverts: the card is taller than the artwork, so behind-the-text needs a scrim
heavy enough that nothing survives. At ≤760px the artwork gets its own 128px strip and the
details sit on the page's own surface, dark on light.

Five deploys, four of which failed the same way and are worth recording:

**Every rule written against `.business-profile-cover` had a `.has-banner` twin carrying one
extra class.** Specificity beats source order, so a fix at the very bottom of the file still
lost. It cost the logo position, the address colour, the card margin and the content padding —
each time the CSS read correctly and did nothing.

Progress only came from querying the live DOM for computed values instead of reading the
stylesheet. Two tools came out of that, in `scripts/ui-verify/`:

- `shot-theme.mjs` — screenshots in a forced colour scheme. The plain screenshot script renders
  whatever the machine prefers, which was dark, and **both** reported faults were light-theme.
- `measure.mjs` — asks the rendered page which elements exceed the viewport. It established
  that a mobile overflow reported earlier **was not real**: it was an artefact of sizing a
  desktop window to phone width rather than emulating a phone.

### Addresses stopped repeating themselves

```
before  ... Nanakramguda Circle, Hyderabad., Nanakramguda, Golconda, Hyderabad, Telangana ...
after   ... Nanakramguda Circle, Hyderabad, Golconda, Telangana, India — 500075
```

The old check asked whether an earlier part _ended with_ the new one, which misses both cases:
the source line ends "Hyderabad." and a full stop defeats it, and "Nanakramguda" sits mid-line.
It compares whole words now.

### English pages were printing Hindi and Telugu

928,540 pages read:

> People look here for कॉलेज, degree, కళాశాల, college, admission and university.

A business stores one keyword array holding every language, because 69 categories carry
translated terms in `searchTerms` and the importer copies them on. That is right for search —
someone typing कॉलेज should find a college — and wrong for a sentence, which speaks one
language at a time. The array stays; the sentence filters to the reader's script. It was in
the meta description too, so it is what Google had been showing.

## 4. SEO

Most of a 55-point specification received that day was already implemented: the title pattern,
self-canonical, `LocalBusiness` with `PostalAddress` and `GeoCoordinates`, `FAQPage`,
`BreadcrumbList`, one H1, conditional FAQs, hierarchical taxonomy, stable ids, segmented
sitemaps, per-entity `lastmod`. What it got right:

### Empty content on 2.9 million pages

Two blocks rendered on essentially every page — one saying nothing had been published, one
saying hours had not been added. **No business in the directory has a listing, and about one in
a hundred has hours.** Identical boilerplate across the corpus, useless to a reader and the
opposite of what makes a page worth indexing. The listings section now renders only when it has
contents, and its tab goes with it.

### The sitemap was missing 570,000 pages

Shard cursors were computed before both imports: 240 shards for 2,961,079 eligible pages.
Recomputed to **297**, with the last shard holding exactly 1,079 URLs (296 × 10,000 + 1,079).

Cursors self-heal after 24 hours, but the first crawler request to trigger it pays a full
recompute — which is precisely the timeout that produced 177 empty sitemaps that morning. They
were written directly instead, so no crawler pays it.

**A trap worth knowing:** the API returned the new count immediately, but the sitemap kept
serving 240 through an API restart, a web restart and a cache-busting parameter. The cause was
Next's `fetch-cache`, which persists on disk across restarts — 1.6 GB of it. Only deleting the
directory clears it.

### The breadcrumb led nowhere Google may follow

Both middle links pointed at `/search`, which `robots.txt` disallows. The trail existed and led
nowhere. It now uses hub pages that already exist:

```
LocZ > Hyderabad > Dental clinics in Hyderabad > Finedent Dental Clinics
```

so every business page passes a link to its city hub and category-in-city hub. The slugs come
from the API rather than from slugifying the display name — that guess is right most of the
time, and a breadcrumb that guesses wrong is a 404 on the way out of the page, multiplied by
four million.

The state is not a level: there is no state page to link to, and a breadcrumb item without a
URL is a dead rung.

### Schema types

Every page declared `LocalBusiness`. `apps/web/src/lib/schema-type.ts` maps category, then
parent, onto the narrowest **real** schema.org type — `Dentist`, `Hospital`, `Pharmacy`,
`Hotel`, `School`, `BankOrCreditUnion`, `GasStation` and about fifty more — falling back to
`LocalBusiness` rather than guessing. Inventing `DentalClinic` because it reads better would be
invalid markup.

### Quality and indexability scoring

`scripts/business-enrichment/quality_audit.py`, over 200,000 businesses:

```
indexability  80-100  66.0%      quality  80-100  60.4%
               60-79  26.0%               60-79  31.7%
               40-59   7.7%               40-59   7.7%
                0-19   0.4%               20-39   0.2%
```

Weights are deliberately unequal — counting fields equally would rate a business with five
social links above one with a street address.

**The answer is that no mass noindex is warranted.** 92% score 60 or above, and every one of
the weakest examples is junk — "Ration Shop", "Anganwadi", "HP" — already excluded from the
sitemap by the junk-name filter, arrived at independently.

### Regression suite

`scripts/ui-verify/seo-check.mjs` — six representative pages, exits non-zero so it can gate a
deploy. Asserts what a crawler reads: status, one H1, canonical, meta description, entity
JSON-LD with address and geo, `BreadcrumbList`, a real AdSense script tag, server-rendered
address, no `aggregateRating` or `review`, and no empty-state boilerplate.

## 5. Monetisation and measurement

### AdSense verification failed, and why

The tag was added with `next/script` and `strategy="afterInteractive"`, reasoning that a
third-party script should not block first paint. That reasoning is sound in general and wrong
for this job: **afterInteractive emits only a `<link rel="preload">` and injects the real tag
from JavaScript after hydration.** AdSense's verifier parses served HTML, found nothing, and
reported "Couldn't verify your site".

The whole point of that tag is that a crawler can read it _without executing anything_. A raw
`<script async>` fixed it, and the site is now verified and listed.

`ads.txt` was returning 404 and now serves the publisher record.

### Ad slot system, shipped switched off

A page asks for a placement, never a provider:

```
BusinessPage → <AdSlot placement="…" /> → placements.ts → provider → AdSense
```

Three business placements: after About (both devices), after Hours (desktop only), before
Nearby (both). **Mobile two, desktop three.** The middle is desktop-only because on a phone it
would sit between the address and the FAQ, which is a lot of advertising on a page someone
opened to get a phone number. The nearby slot sits _above_ that list — those are internal links
people navigate by, and an ad among them reads as a result.

Four independent gates must all open: `NEXT_PUBLIC_ADS_ENABLED`, the client id, the placement's
own slot id, and a content score counting **real fields** (address, landmark, hours, website),
so a sparse page carries one ad and a rich page three, and no amount of padding qualifies a
page for more.

CLS is guarded by reserving each placement's height; below-fold slots wait on an
`IntersectionObserver`; an unfilled unit collapses rather than leaving a hole.

### Analytics, deliberately before the ads

The site carried **no analytics of any kind**, so the question the monetisation plan asks —
does an extra unit earn more than it costs in calls? — was unanswerable at any price.

GA4 went in, then seven business actions: directions, call, website, email, enquiry, claim,
share, each carrying business id, category, city and locality. Verified at runtime rather than
by grepping HTML: `gtag` is a function, `dataLayer` grows on click, and `directions_click`
reaches `google-analytics.com/g/collect`.

One delegated listener, not an `onClick` per link — converting those into client components
would move critical server-rendered content behind hydration on three million pages to gain
nothing a listener cannot do. The anchors stay plain `<a>` elements with `data-track`; if the
listener never mounts they still work, because they are links, not handlers.

**A baseline collected after ads go live is not a baseline.** Let it run a week or two first.

## 6. Admin panel audit

**Security is properly built.** Global `JwtAuthGuard` and `PermissionsGuard` via `APP_GUARD`,
with `@RequirePermissions` per endpoint. Tested rather than read: every endpoint returns 401
unauthenticated, including `POST /admin/jobs/:name/run`, which would be the dangerous one.

**One performance fault, fixed.** The overview runs about seventeen counters in parallel.
Sixteen return in 44–48 ms; the seventeenth counts 4.2 million businesses and took 2,494 ms, so
`Promise.all` waited on it and a page of mostly single-digit numbers took two and a half
seconds. Memoised for five minutes — five rather than a day because an admin who has just run
an import expects the number to change, and a memo rather than `pg_class.reltuples` because a
dashboard that disagrees with a plain `count(*)` is one people stop trusting.

Worth noting: `users` is 9 and `published listings` is 1. The panel is built for a scale of
activity the platform has not reached, so most screens are untested against real volume.

## 8. Lessons, stated plainly

**A green build sees nothing.** Three faults shipped that typechecked cleanly: a banner behind
a scrim, a name clipped off a phone, an AdSense tag that never reached the HTML.

**Read the values, not the count.** Mandal looked 0% and was 21%. Coverage numbers say nothing
about whether the data means anything — "Nil" was stored 578 times.

**Ask the browser.** Four CSS fixes read correctly and did nothing until the live DOM was
queried for computed values.

**Verify the thing the consumer consumes.** AdSense needed HTML, so grep was right there and
useless for analytics; GA4 needed execution, so runtime checks were right there and grep would
have lied.

**Bound every query.** On a 4.2M table the difference between a bounded and an unbounded query
is an outage, not a slow response.
